# Skill - Slide Deck Generation

## Purpose
Build an executive-grade slide deck from a folder of per-slide markdown files, then verify the rendered visual output before reporting completion. Output is a self-contained HTML file viewable in a browser and exported to PDF via the hybrid builder. Charts via Chart.js (loaded from CDN, rendered natively by the browser). Consistent CSS styling controlled by one stylesheet. 16:9 landscape by default; clean executive register (black, navy accent, generous whitespace).

**Design from the template gallery.** The catalog of layouts in [tools/slides/_gallery/](tools/slides/_gallery/) is the preferred source of inspiration for every deck — browse it first and pick the templates that fit your story rather than writing slides from scratch. See *Designing a deck: start from the gallery* below.

## Trigger
Use this skill when the user asks to:
- Build a slide deck
- Turn a memo or set of notes into a presentation
- Create a read-out deck for a leadership meeting
- Generate slides from markdown content
- Produce an HTML / PDF deck with a specific style

Typical trigger phrases:
- "build me a deck for [audience]"
- "turn this memo into a presentation"
- "create the slides for the [meeting] read-out"
- "make a deck with these N slides"

## Scope
- Output: a self-contained HTML file viewable in any modern browser (Chrome, Safari, Firefox), exportable to PDF via the browser's Print to PDF.
- Format: 16:9 landscape (1280 × 720 nominal, prints at 13.333 × 7.5 inches).
- Charts: Chart.js v4 via CDN, embedded inline as `<canvas>` + `<script>` per chart.
- Tables, bullets, callouts, two-column layouts, speaker notes all supported.
- Speaker notes mode: optional `deck-notes.html` build that shows notes under each slide for rehearsal.
- Visual QA is mandatory: every generated slide must be rendered in a headless browser, checked for overflow/clipping, and visually inspected from screenshots before the task is considered done.

## How It Works

A deck lives in its own folder. The folder contains numbered markdown files (one per slide) plus an optional `deck.yaml` for deck-wide metadata. The build script reads all markdown files in filename-sorted order, parses each one's frontmatter, applies the matching template, concatenates the rendered slides into one HTML file, and embeds the shared CSS plus the Chart.js CDN reference.

```
<deck folder>/
├── deck.yaml                       # optional deck-wide metadata
├── 01_title.md
├── 02_agenda.md
├── 03_executive_summary.md
├── 04_diagnosis.md
├── ...
├── 12_decisions.md
├── deck.html                       # output (generated by build script)
└── deck-notes.html                 # output if --with-notes (generated)
```

## Designing a deck: start from the gallery

**The gallery is the preferred starting point for every deck.** Before writing any slides, open the live gallery and browse it for inspiration — it renders one example slide for each template in the catalog, so it is the fastest way to see what layouts exist and pick the ones that fit the story you're telling.

```bash
cd 15_Skills/tools/slides/_gallery
./switch_theme.sh default       # or any brand theme you've added
python3 ../build_deck.py .
open deck.html                  # browse every template side by side
node ../build_deck_pdf.mjs deck.html   # or read it as a PDF
```

Workflow for a new deck:

1. **Browse the gallery** (and skim [tools/slides/PATTERNS.md](tools/slides/PATTERNS.md)) and shortlist the templates that match each beat of your narrative — a title, a way to frame the diagnosis, the right chart or comparison layout, a decisions/asks slide, a closing.
2. Mix freely. A deck is a sequence of whatever templates tell the story best; you are not limited to the handful shown below. Reach for the creative templates (big-number, visual metaphors, magazine cover, storyboard) when a slide deserves more than a bullet list.
3. Copy the frontmatter contract for each chosen template from PATTERNS.md, fill in your content, and build.

The catalog is the design palette; the five templates documented below only exist to illustrate the markdown/frontmatter mechanics. Don't treat them as the menu.

## Slide Markdown Format

Each slide is a markdown file with frontmatter declaring the template and per-slide variables, plus a body of markdown content that gets rendered into the template's `{{body}}` placeholder. The five templates below illustrate the basic mechanics; the full catalog (and the gallery above) is where you actually choose layouts.

### Template: `title`

The opening slide. Cover-style block with eyebrow label, headline, subtitle, and a metadata grid.

```markdown
---
template: title
eyebrow: "DRAFT FOR DISCUSSION"
title: "[Deck title]"
subtitle: "[One-line subtitle for the deck]"
prepared_for: "[Audience / organisation]"
prepared_by: "[Author / team]"
date: "[Date]"
status: "Draft"
---
```

### Template: `agenda`

A numbered agenda using two-column grid. Body is a standard markdown ordered list; the CSS auto-numbers the items with a deep-blue accent.

```markdown
---
template: agenda
title: "Agenda"
eyebrow: "OVERVIEW"
---

1. Executive summary
2. Situation and diagnosis
3. Recommendation
4. Plan and next steps
...
```

### Template: `content`

The workhorse template. Title, optional subtitle line, body area for bullets / tables / callouts / charts / two-column layouts. Optional speaker notes.

```markdown
---
template: content
title: "[Slide headline]"
subtitle: "[Optional one-line subtitle]"
eyebrow: "SECTION LABEL"
notes: |
  Speaker notes for this slide. Lead with the headline point, then expand.
---

- **First point.** Plain-text continuation of the lead bullet.
- **Second point.** One idea per bullet; keep it to a single line where possible.
- **Third point.** The bold phrase anchors the bullet; the rest carries the detail.
- **Fourth point.** Three to five bullets max; the voice-over carries the rest.
```

### Template: `section_divider`

A cover-style break slide for marking transitions between major sections. Use sparingly.

```markdown
---
template: section_divider
title: "[Section title]"
subtitle: "[Optional one-line lead-in for the section]"
eyebrow: "PART THREE"
---
```

### Template: `closing`

Final slide. Centred, cover-style. Typically "Thank you" or "Discussion" framing.

```markdown
---
template: closing
title: "Decisions sought today"
subtitle: "Five things to confirm in this session"
---
```

## Chart.js Charts

Charts are written as raw HTML inside the markdown body. Pandoc passes them through unchanged when `raw_html` is enabled; the built-in fallback renderer also preserves raw HTML blocks used by this slide system. Use a unique `id` per chart canvas.

```markdown
---
template: content
title: "[Chart slide headline]"
---

<div class="chart">
  <canvas id="value_breakdown" width="600" height="280"></canvas>
  <div class="chart-caption">Indicative annualised value, currency / year.</div>
</div>

<script>
  new Chart(document.getElementById('value_breakdown'), {
    type: 'bar',
    data: {
      labels: ['Lever A', 'Lever B', 'Combined'],
      datasets: [{
        data: [5, 15, 20],
        backgroundColor: ['#1f4287', '#1f4287', '#c9a96e']
      }]
    },
    options: {
      responsive: false,
      plugins: { legend: { display: false } },
      scales: { y: { beginAtZero: true, title: { display: true, text: 'value / year' } } }
    }
  });
</script>
```

## Deck-wide Metadata (`deck.yaml`)

Optional. Sets defaults that apply to every slide unless overridden in the slide's own frontmatter.

```yaml
title: "[Deck title]"
footer_left: "Confidential draft — [date]"        # text goes LEFT
footer_right: ""                                  # left empty when brand_footer is set; logos render here
brand_footer: "assets/co_brand.png, assets/client_brand.png"
```

**Footer convention:** brand / co-brand logos render in the RIGHT footer slot; classification / date text sits in the LEFT slot. When `brand_footer` is set, it overrides the `footer_right` text (so leave `footer_right` empty in `deck.yaml` and put the date in `footer_left`). Do not change this default without an explicit user instruction for a particular deck.

### Export to PDF

```bash
# Default: HYBRID PDF — looks identical to the HTML in every viewer + crisp selectable text.
node 15_Skills/tools/slides/build_deck_pdf.mjs <deck_folder>/deck.html
# → writes <deck_folder>/deck.pdf

# Options:
node 15_Skills/tools/slides/build_deck_pdf.mjs <deck_folder>/deck.html --truevector  # tiny + true vector, but card shadows may seam in Quartz/Preview
node 15_Skills/tools/slides/build_deck_pdf.mjs <deck_folder>/deck.html --raster       # pixel-perfect screenshots, text NOT selectable
```

**Default is HYBRID** — the only mode that is BOTH pixel-identical to the HTML in every PDF viewer AND has crisp, selectable vector text. It works in two passes: (1) hide all text and screenshot each slide, so the screenshot carries only what must be raster to render correctly everywhere (soft card box-shadows, Chart.js canvases, logos, fills); (2) place that text-free screenshot behind the slide and render the slide's **real text on top as true vector** — selectable, searchable, copy-pasteable, crisp at any zoom. Same structure and end result as PowerPoint → PDF. Typical output is well under 1 MB.

**Why not plain `page.pdf()` vector (the `--truevector` mode):** Chromium emits each CSS `box-shadow` as a separate PDF soft-mask. Poppler (`pdftoppm`) composites these cleanly, but **macOS Quartz — Preview, Quick Look, the VS Code / IDE PDF viewer — double-darkens the seam where two adjacent cards' shadow masks meet**, drawing an ugly hard grey band down the inner edge of every card except the first. The PDF looks fine in one renderer and broken in another. The hybrid sidesteps this because its visible layer is a flat raster (no soft-masks to misrender).

**CRITICAL verification rule (MANDATORY, every deck):** building the PDF is not done until you have **rendered the actual PDF with a Quartz-based engine and read the pages as images** — `pdfseparate -f N -l N deck.pdf page.pdf` then `sips -s format png page.pdf --out check.png`, or Quick Look (`qlmanage -t`). The HTML headless QA does **NOT** catch PDF-only artifacts: the hybrid builder paints fills/borders into a raster backdrop and the text as a separate vector layer, and on some layouts the backdrop drifts relative to the text (e.g., a CSS `border`/box landing a row away from the text it should wrap). You will only see that by inspecting the PDF itself. Do **NOT** verify only with `pdftoppm` / poppler: poppler hides both the shadow-seam artifact and masks alignment drift, so a poppler-only check will tell you a broken PDF is fine. Also inspect at high resolution; a subtle shadow looks "missing" at 110–150 dpi but is fine at print resolution.

**NEVER switch to `--raster` to "fix" a hybrid-PDF rendering artifact.** Raster strips selectable text from the entire deck, which is not acceptable for shareable documents. Fix the root cause in CSS instead. The reliable trick: the compositor strips `border-color`/`background`/`box-shadow` from the real elements (they live only in the raster backdrop) but it does **not** strip `outline` — so render highlight boxes with `outline` (optionally suppressed during capture via `html.__capture <selector> { outline: none !important; }`) so the box paints in the vector pass, locked to its text, and stays aligned in the PDF.

**Logos must be truly transparent.** A logo PNG with an *opaque* background that happens to match the slide colour looks fine in the HTML (the colours blend), but a PDF can reveal the logo's background as a faint rectangle. Always use a transparent-background logo (alpha 0). If you only have an opaque one, colour-key its background to transparent first (Pillow: set pixels within tolerance of the bg colour to alpha 0) and reference the transparent version. This is in addition to the logo-pixel-inspection rule above.

Requires playwright + chromium installed locally. On first use, install them once in the deck folder:

```bash
cd <deck_folder>
mkdir -p .maxos/visual-check && cd .maxos/visual-check
npm init -y >/dev/null && npm install --no-audit --no-fund playwright
npx playwright install chromium
```

(The visual-QA tool already requires playwright, so most decks have it installed already.)

Avoid the browser's File → Save as PDF for decks with card shadows: it uses the same Chromium print pipeline as `--truevector`, so the shadow-seam artifact described above will appear in Quartz-based viewers (Preview / Quick Look / IDE). Use the hybrid builder instead.

This hybrid pipeline is verified across the **entire template gallery** (all 98 `_gallery/` templates — titles, agendas, frameworks, charts, tables, the McKinsey exhibit pack, scored matrices and scoreboards, bar-gauges, bubble plots, ecosystem orbits, dark slides, big-typography, and the SVG visual metaphors like iceberg / concentric-rings / venn): every one renders identically to its HTML in Quartz with selectable vector text. (The builder awaits backdrop-image decode before printing, so decks of any length composite correctly; an earlier version raced and blanked fills on large decks.) So it is the standard way to produce a deck PDF for any template in the catalog.

## Images and Logos

Each deck may contain an `assets/` subfolder. Images placed there are referenced from slides via standard `<img>` tags or markdown image syntax. The `--embed-assets` flag base64-inlines them so the rendered HTML is self-contained.

### Mandatory: inspect every logo asset before using it

**Failure mode this prevents:** a past deck rendered a white rectangle on the title slide because the chosen logo PNG had a near-black baked-in background that a CSS filter then inverted. Another logo with a dark grey baked-in background was placed onto a white content slide and read as a dark rectangle pasted on the page.

Before referencing any logo in `cover_logo` or `brand_footer`, **inspect the actual pixel content** of the file. A logo PNG can be one of:

| Background pixel | Safe on | Unsafe on | Conventional filename hint |
|---|---|---|---|
| Transparent (alpha 0) | Any slide | None | `*_transparent.png` |
| White (alpha 1, RGB ≈ 255) | White slides | Dark slides (renders as a white box) | `*_on_white.png` |
| Dark (alpha 1, RGB ≈ low) | Dark slides matching the asset's specific shade | White slides (renders as a dark box) | `*_on_dark.png` or `*_on_<hex>.png` |
| Brand colour | Slides matching that colour | Everything else | `*_on_<colour>.png` |

**Always verify with Pillow** before writing the slide markdown. A four-line script:

```python
from PIL import Image
img = Image.open("assets/your_logo.png").convert("RGBA")
print(img.getpixel((1, 1)))    # top-left corner pixel
print(img.getpixel((img.size[0]//2, img.size[1]//2)))  # centre pixel
```

If the background is white, the logo can sit only on white slides. If the background is dark, the logo can sit only on a slide whose CSS `--color-cover-bg` matches that exact colour. The build script runs the same check automatically and prints `[LOGO SAFETY]` warnings if the logo background mismatches the target slide background; **do not ignore those warnings**.

Filenames are hints, not guarantees. The skill cannot trust the filename. Always sample the pixel.

### Cover-slide logo block (title and closing templates)

Add `cover_logo:` to the slide frontmatter. The build script renders a logo block above the eyebrow / headline. Single path or comma-separated for multiple logos:

```yaml
---
template: title
cover_logo: "assets/your_logo_transparent.png"
eyebrow: "DRAFT FOR DISCUSSION"
title: "[Deck title]"
---
```

### Footer brand strip (content and agenda templates)

Add `brand_footer:` to either deck.yaml (applies to every content slide) or per-slide frontmatter. When set, the brand strip renders **inside the footer's right slot**, replacing whatever text was in `footer_right`. The classification / date text sits in `footer_left` (the LEFT slot). This is the established convention — don't override unless the user asks for a specific deck.

```yaml
# deck.yaml
title: "[Deck title]"
footer_left: "Confidential draft — [date]"         # LEFT: text
footer_right: ""                                   # RIGHT: filled by brand_footer logos
brand_footer: "assets/author_logo.png, assets/client_logo.png"
```

### Inline images in markdown body

Standard markdown / HTML works. Useful CSS classes already on hand:

- `logo-top-right` — small logo absolutely positioned in the slide's top-right corner.
- `brand-footer` / `brand-footer-logo` — used by the footer brand strip pattern above.

```html
<img src="assets/some-image.png" class="logo-top-right" alt="Brand logo">
```

## Reusable Patterns Library

Before building a new deck, **read [tools/slides/PATTERNS.md](tools/slides/PATTERNS.md)**. It documents:

- The typography defaults baked into [`deck.css`](tools/slides/deck.css) (38px title, 19px subtitle with 36px margin, h3 with 12px bottom margin, agenda body vertically centred). Don't override these in a `theme.css` without a reason — they reflect preferences validated across exec read-out decks.
- The reusable layout patterns: `.capacity-row` / `.capacity-card` (titled cards with eyebrow + bullets), `.callout.capacity-kicker` (meta-message below a row of cards), `.two-col` with `class="col"` children, `.metric-card`.
- The **raw-HTML table pattern** for fixed column widths — pandoc's pipe-table renderer emits a `<colgroup>` with equal 25% widths that overrides any CSS, so per-column widths only work when the table is written as raw HTML in the markdown.
- Pandoc gotchas: bare `<div>` wrappers stripped, indented raw HTML rendered as code, etc.

**Promote, don't duplicate.** If you write the same per-deck layout twice (or come up with a new general-purpose pattern), promote it into [`deck.css`](tools/slides/deck.css) and add a markdown example to [`PATTERNS.md`](tools/slides/PATTERNS.md). A `theme.css` should only contain palette / font / brand-asset wiring plus narrowly-scoped fixes for a particular slide (`.slide[data-slide="N"] ...`).

## Per-Deck Theme Override (`theme.css`)

A deck folder can include a `theme.css` file alongside its slide files. The build script loads it _after_ the global `deck.css`, so its rules take precedence. Use this to set a brand palette per deck without touching the shared CSS.

Pattern: override the `:root` CSS variables and add brand-specific @import statements for fonts.

```css
/* <deck folder>/theme.css */
@import url("https://fonts.googleapis.com/css2?family=Nunito+Sans:wght@400;600;700&family=Barlow:wght@300;400;500;600&display=swap");

:root {
  --color-accent: #9A4E9E;           /* brand mid-tone accent */
  --color-accent-soft: #efefef;
  --color-cover-bg: #5C2F7E;         /* brand deep cover background */
  --color-cover-accent: #9f81d0;     /* lighter accent for the cover */
  --color-text: #252525;
  --color-rule: #cecece;
  --color-faint: #b3b3b3;
  --font-sans: "Barlow", "Nunito Sans", -apple-system, "Helvetica Neue", sans-serif;
}

.slide__title,
.title-headline,
.section-title,
.closing-headline,
.slide__eyebrow,
.title-eyebrow,
.section-eyebrow {
  font-family: "Nunito Sans", "Barlow", -apple-system, "Helvetica Neue", sans-serif;
}
```

## Mandatory Headless Visual QA

Never report that a deck is done based only on successful HTML generation. HTML slide decks are visual artifacts; the skill is incomplete until the actual browser-rendered slides have been inspected by reading the image bytes.

After every deck build:

1. Render `deck.html` in a headless browser at the deck's native slide size.
2. Capture one screenshot per `.slide`.
3. **Run a structural check first** (`check_deck_visual.mjs`) for:
   - vertical or horizontal scroll overflow;
   - visible elements outside the slide bounds;
   - body content colliding with the footer;
   - blank or failed chart/canvas regions;
   - text pushed off-slide, overlapping, or too small to read;
   - tables that squeeze important content into unreadable columns.
4. **Then read at least one screenshot per slide as an image** (do not stop at the structural check). The structural check catches overflow and clipping; it does NOT catch white-logo-on-white-slide, dark-logo-on-white-slide, footer collision with absolute-positioned elements, or other "looks wrong but technically fits" issues. Read the PNG bytes.
5. Iterate on slide content, CSS, templates, or chart design until every slide passes BOTH the structural check AND visual reading.
6. **Then export the PDF and inspect the PDF itself with a Quartz engine** (`pdfseparate` + `sips`, or `qlmanage`), reading the rendered pages as images. The HTML render and the PDF can disagree: the hybrid builder's raster backdrop can drift relative to the vector text layer, so boxes/borders/outlines that look perfect in the HTML can be misplaced in the PDF. This step is mandatory and is the only way to catch it. Keep the default hybrid (selectable-text) export; never fall back to `--raster` to mask a rendering bug — fix the CSS (see the `outline` trick under *Export to PDF*).
7. Only then report completion.

### What "looks wrong but technically fits" means

These pass the structural check and need a human (or agent) eye on the screenshots:

- A logo with a baked-in white background placed on a white slide (looks invisible / merges with the page).
- A logo with a baked-in dark background placed on a white slide (looks like a dark rectangle pasted on the page).
- A CSS filter (`brightness(0) invert(1)` or similar) applied to a non-transparent logo, turning the entire image into a solid block.
- Two elements occupying the same coordinate region with one obscuring the other (e.g. a brand-footer logo over a date text).
- Colour contrast that's technically rendered but visually unreadable (e.g. lavender text on a light grey background).

**Do not skip the image-read step.** The agent must literally view the PNG bytes before reporting the deck is done.

Use the tracked visual checker:

```bash
node 15_Skills/tools/slides/check_deck_visual.mjs <deck_folder>/deck.html
```

The checker writes screenshots, contact sheets, and `report.json` under `.maxos/visual-check/screenshots/`. `.maxos/` is ignored local runtime state.

## Viewing and Exporting

1. **Browser view:** double-click `deck.html` (or `open deck.html` in macOS Terminal). Slides display in landscape 16:9 with charts rendered.
2. **PDF export:** run `node 15_Skills/tools/slides/build_deck_pdf.mjs <deck_folder>/deck.html`. This is the standard, supported way to produce a deck PDF (hybrid mode: identical to the HTML in every viewer + selectable text — see *Export to PDF* above). Don't hand-export from the browser for shadowed decks.
3. **Speaker-notes PDF:** open `deck-notes.html` and print the same way. Slide heights expand to accommodate the notes block.

## Dependencies

- `python3` (standard library only; frontmatter parsed inline)
- `pandoc` preferred for Markdown rendering, but the build script has a built-in fallback for the slide Markdown subset
- `node` + Playwright/Chromium for mandatory headless visual QA
- Chart.js is loaded via CDN at view time

No WeasyPrint is needed. The browser is both the final renderer and the required visual QA engine.

## Styling and Customisation

All styling lives in [tools/slides/deck.css](tools/slides/deck.css). Adjust the CSS variables at the top of that file to shift colours, fonts, slide dimensions. The accent colour, title-cover background, and typography all sit in `:root`.

Per-deck overrides can be added by writing a `custom.css` next to the slide files; the build script does not pick that up automatically yet (a v2 feature). For now, modify `deck.css` for global changes.

## Conventions

- One markdown file per slide. Filename prefix controls slide order (`01_*.md`, `02_*.md`, ...).
- Keep slide content sparse. Three to five bullets max per content slide; the voice-over carries the rest.
- Use `**bold**` to anchor a bullet's headline phrase, then continue in plain text.
- Use the `notes:` frontmatter field for speaker notes; they only render in `--with-notes` mode.
- Use callouts (`<div class="callout">...</div>`) sparingly to highlight one key point per slide.
- For charts, use distinct colours from the accent palette in the CSS. Avoid more than two colours per chart.
- Prefer metric cards or compact tables over charts when a chart makes the slide overflow or reduces readability.
- Do not solve overflow by making text unreadably small. Cut content, split the slide, or change the layout.

## Limitations and v2 Candidates

- Charts use Chart.js via CDN — requires internet on first browser load. Self-host the script in `tools/slides/lib/chart.umd.js` if offline use is needed.
- No automatic table of contents linking across slides yet.
- No multi-deck composition (one deck per folder).
- Per-deck CSS overrides not yet wired in.
- Chart.js charts (and any `<canvas>`) export as raster inside the otherwise-vector PDF. This is inherent to canvas; slide text around them stays selectable. If a chart must be vector, render it as inline SVG instead of a canvas.
